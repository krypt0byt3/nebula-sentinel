# MITRE ATT&CK coverage map

This file is a **best-effort, source-grounded** mapping of the detection logic
actually implemented in `nebula-agent` to MITRE ATT&CK (Enterprise) technique
IDs. It is generated by reading the detector modules, not aspirationally: a
technique is listed only where code genuinely emits a detection (or a heuristic
hit) for behavior corresponding to it. Where a mapping is partial, heuristic, or
telemetry-dependent, it says so. Last generated from source: **2026-10-29**.

Each technique in ATT&CK is one an adversary performs; a detector here claims it
only when the agent observes a concrete artifact of that behavior. Coverage is
**not** a security guarantee — most of it is behavioral/heuristic and can be
evaded. Treat this as a map of *what is wired*, for gap analysis and tuning.

## How to read the confidence tiers

| Tier | Meaning |
|------|---------|
| **Behavioral** | Fires on observed runtime behavior (I/O pattern, process ancestry, transfer shape). High fidelity, transport/family-agnostic, hard to spoof. |
| **Heuristic** | Command-line / path / process-name string matching. Broad breadth, but evadable by renaming, obfuscation, or LOTL. This is the `anomaly` engine's tier. |
| **Signature** | Operator- or intel-supplied rules (YARA/Sigma/Wazuh) and hash reputation. Fidelity depends entirely on the loaded ruleset/intel. |
| **Config / static** | Scans configuration or images at rest (IaC, container images, posture). Detects *misconfiguration that enables* a technique, not live execution of it. |
| **File-integrity** | inotify/FSEvents on a fixed watchlist of sensitive paths. High fidelity for the watched paths only. |

## Summary

- **14 / 14** ATT&CK Enterprise tactics have at least some coverage.
- **~138** distinct base techniques and **~276** technique/sub-technique IDs are
  referenced by live detection code across the modules below.
- The breadth number is dominated by one module: `anomaly/mod.rs` is a
  single-event heuristic engine that its own header describes as "196
  technique/sub-technique heuristics" spanning all 14 tactics. It supplies the
  long tail; the specialized modules below supply the high-fidelity depth.

## Gaps / not yet covered (honest)

1. **Reconnaissance (TA0043) and Resource Development (TA0042) are effectively
   uncovered.** These are *pre-compromise, off-host* adversary activities. A
   host endpoint agent can only see them if the tooling happens to run on a
   monitored machine, so the handful of `anomaly` heuristics (T1595/T1596/T1590/
   T1591, T1587/T1583) fire narrowly and are easily missed. Do not treat these
   tactics as meaningfully monitored.

2. **The breadth is heuristic, and heuristic means evadable.** The bulk of the
   ~138 techniques come from `anomaly/mod.rs`, which matches on command-line
   strings, process names, and paths from single events. Renaming a binary,
   base64/obfuscating a command, or living off the land defeats these. The
   high-fidelity, hard-to-spoof coverage is the much smaller set carried by the
   behavioral modules (`ransomware`, `zeroday`, `dlp`, `network_monitor`, `apt`,
   `fim`, `secrets_scan`). Coverage breadth should not be read as detection
   confidence.

3. **Some mapped techniques are documented but not emitted.** `dlp/mod.rs`'s
   header lists T1020, T1030 (Data Transfer Size Limits) and T1052 (Physical
   Medium), but the code emits only T1041/T1048/T1005/T1074/T1560; T1030/T1052
   have **no detection path**. Treat header-only IDs as design intent, not
   coverage.

Additional, lower-priority gaps worth noting:

- **Telemetry-dependence / platform skew.** Many Windows-flavored mappings
  (registry Run keys, DPAPI, token manipulation, Kerberos) are command-line
  heuristics rather than real registry/Event-Log/ETW telemetry; on Linux-first
  builds the underlying signal may never be populated. The `anomaly` header
  itself documents Linux-centric assumptions and per-platform compilation.
- **Cloud / SaaS control-plane** (TA0006/TA0009 cloud variants) is covered only
  by static IaC scanning (`iac`) and the single cloud-metadata network check
  (T1552.005); there is no live cloud-API/audit-log monitoring.
- **Signature-tier techniques inherit their rules.** `yara_scan`, `sigma`, and
  `rules` carry whatever technique IDs the loaded YARA/Sigma/Wazuh rules declare
  — the agent provides the engine, not the coverage. An empty ruleset = no
  coverage from these modules.
- **`baseline`** detects statistical novelty/rarity but is deliberately
  **technique-agnostic**: it raises "this is abnormal for this host" without an
  ATT&CK label, so it contributes confidence fusion rather than technique
  coverage.
